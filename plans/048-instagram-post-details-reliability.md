## Settled contracts

### Target scope and outcomes

At launch, freeze a versioned manifest from catalog rows using normalized account identity, platform, requested date bounds, selected task mask, freshness-policy version, and launch/run identity. Include catalog-only posts; normalize and deduplicate shortcode/source identities. Empty scope is explicit successful no-work. Invalid catalog identifiers remain counted as invalid/unresolved with a reason; never silently drop them. Posts discovered later belong to a subsequent run. A rerun after a completed run makes a new manifest; a retry/resume keeps the same manifest.

Add a narrowly scoped durable target relation through an additive migration, proposed social.instagram_detail_run_targets, and compact run-manifest metadata in existing run config. Before coding, verify whether an existing table supplies these exact guarantees; reuse it if equivalent rather than duplicate it. Required target columns: run_id, source_id, deterministic target key, required task/field mask, policy version, state, attempt_count, next_attempt_at, lease_owner, lease_generation, lease_expires_at, fetched_at, committed_at, error_code, compact redacted error summary, and per-phase elapsed milliseconds. Unique(run_id, source_id); indexes support run/state/next_attempt_at/key and lease expiry. Confirm foreign-key, RLS/service-role, and retention conventions from neighboring migrations. No whole-account payload JSON inside the manifest.

States: pending -> leased -> committed | cached_satisfied | source_unavailable | retry_wait | failed. Cancellation releases uncommitted leases to pending or records cancellation without inventing success. An expired lease is reclaimable with a higher generation. failed and retry_wait remain unresolved for completion. source_unavailable requires explicit evidence for a deleted/private/inaccessible post from a healthy authenticated transport; 401, 429, challenge, timeout, parse error, redirect loop, and unknown 404 are operational failures, never permanent unavailability. Missing required fields are a partial result and remain unresolved for those fields.

Snapshot equation: total = committed + cached_satisfied + source_unavailable + unresolved. The four buckets are disjoint target counts. unresolved includes pending, leased, retry_wait, and failed. attempted, fetched, and requests are separate cumulative activity counters and may exceed target counts. Report committed as genuinely fetched-and-persisted satisfaction, not merely touched rows. completed requires unresolved=0; source_unavailable yields an explicit completed-with-unavailable presentation, not a claim that every post was refreshed. A terminal failed/cancelled run retains its unresolved count and resume path.

Per-field successful observation timestamps advance only for fields actually obtained from a successful response. metadata_attempted_at/error diagnostics may advance on a failed attempt, but metadata_scraped_at and metric observation timestamps cannot. Cached satisfaction does not manufacture a fetch timestamp. Preserve generic scraped_at compatibility for other consumers; redefine its use for this path explicitly and migrate the UI away from inferring success from it.

### Dispatch and transaction ownership

Use an atomic conditional reservation before the external Modal spawn: reserve a dispatch generation/token and lease in the job row with expected status and owner. Commit before network spawn; never hold a database connection/transaction across the provider call. Bind the resulting call ID using compare-and-set on that token. A concurrent dispatcher cannot reserve an unexpired generation. Worker claims require the same token; a late worker or late dispatcher cannot overwrite a newer generation. Keep the existing worker/job owner checks and make them mandatory for this path.

Provider spawn and database commit are not one transaction. If spawn succeeds but ID persistence fails, retain the reserved generation and mark spawn outcome uncertain; reconcile by token/provider evidence before another dispatch. If no reliable provider lookup exists, wait for reservation/worker-heartbeat expiry and fence the old token before issuing a replacement. Duplicate computation is possible at this boundary, but only one current generation may commit targets or complete the job. Never claim exactly-once external invocation.

Completion receipt version 1 contains run_id, job_id, dispatch_generation, worker identity, claimed=true, manifest identity/version, and committed outcome totals. Persist the authoritative receipt and terminal job transition in the same guarded database transaction after target reconciliation. Modal transport completion alone is insufficient; claimed=false is a no-op. Inspect failed/timeout calls as failure evidence for their owning generation. Unknown provider state remains unknown and does not clear the active owner. Readers must handle receipt-absent legacy jobs conservatively; never synthesize new receipts from old saved counts.

For each write batch, keep pending results until commit succeeds. Atomically persist detail/metric changes, required canonical/sidecar observations, and target outcomes. Publish progress/returned rows only after commit. If connection loss makes commit outcome uncertain, query target generation/idempotency keys before replay. Observation uniqueness must prevent a replay from adding duplicate history. Do not mark a target committed while its required writes are outstanding.
